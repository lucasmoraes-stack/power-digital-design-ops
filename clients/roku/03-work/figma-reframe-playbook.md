# Figma aspect-ratio reframe — technique playbook

Internal notes, not client-facing. Written after reframing 61 approved 16:9 Roku ad scenes into 9:16 and 1:1 (122 new frames total) across 5 Figma sections, using ~24 parallel subagents over two sessions. Everything below was learned the hard way — each item caused a real bug or a real judgment call during the work. If this pattern gets reused on another client, consider promoting the reusable parts into a shared, client-agnostic location in this repo; it's filed under Roku for now because it's only been proven on this one client.

## Setup that made parallel agents safe

1. **Reserve every destination frame before any composition work starts.** One mechanical pass creates all target frames (gray placeholder fill, `placeholder = true`, correct final size) up front, laid out in new rows inside the same section, named `9x16 - Scene NN (src {original-id})` / `1x1 - Scene NN (src {original-id})`. Composition agents then only ever write inside their own pre-assigned frame IDs. This is what makes running many agents concurrently against the same Figma file safe — no agent ever has to decide where to put a new top-level frame, so there's no collision risk even though they're all mutating the same document at once.
2. **Group scenes by shared composition, not by sequence position.** A storyboard's 17-23 sequential scenes usually decompose into 5-10 real "beats" (near-duplicate hold frames, transition frames, and one-off cards) — group by that, not by literal scene order, so one agent becomes the expert on one recurring layout instead of re-deriving it 20 times.
3. **Across near-identical campaign variants (e.g. 3 carousels with the same 7-position structure but different copy), group by position across variants instead of by variant.** One agent handling "position 3 across all 3 carousels" reuses the same composition recipe 3 times; one agent handling "all 7 positions of 1 carousel" has to solve 7 different problems. The former is both faster and more consistent.
4. **Give each agent the specific node IDs, not just descriptions.** "The headline scene" is ambiguous across 5 sections that reuse the same copy; `origem "26:897" → destino 9x16 "29:4"` is not.

## The locked-font problem ("Roku Display" doesn't load in the plugin sandbox)

This was the single biggest source of bugs. `figma.loadFontAsync` fails for it, `listAvailableFontsAsync` doesn't list it — but the font renders fine in Figma's own screenshot/render service, so screenshots always look correct even when the *editing* API can't touch the text safely.

- **Never call `resize()` or edit `characters`/`fontName` on a text node whose font can't load.** The box freezes; a resize corrupts or clips it without erroring first.
- **Safe operations:** `clone()` (always works, font or no font), then reposition via `x`/`y`. That covers most of the reframe work, since text content never needs to change.
- **When a clone needs to shrink or grow** (e.g. the source text is wider than the new 1440px canvas): wrap the clone in `figma.group([clone], parent)` and call `group.rescale(factor)`. This is a pure geometric transform — it scales `fontSize`, width, height, and position together — so it works without the font loaded. Do not try to set the scale via `relativeTransform` directly on the TEXT node itself; Figma silently ignores a scale component set that way on text.
- **`group.resize()` is not the same as `group.rescale()`.** If the group's only child is a single TEXT node, `resize()` passes straight through to the text node and corrupts it the same way a direct `resize()` would. Use `rescale()` for anything containing text.
- **Don't trust the reported `height` of an unloaded-font autosize text node.** It can under-report real glyph height significantly, which causes silent overlaps with sibling elements (underlines, dividers) that only show up in a screenshot, not in the numbers.
- **`loadFontAsync` failing is expected, not a blocker** — confirm it fails once per session (so you're not guessing), then route everything through clone + reposition/rescale instead of trying repeatedly.

## Shape / boolean bugs

- **`clone()` immediately followed by `resize()` on an `ELLIPSE` can silently produce an invisible node** (`absoluteRenderBounds: null`, even though fills and effects look fine). If a rescale/resize is genuinely needed on an ellipse, build it fresh with `figma.createEllipse()` instead of cloning one.
- **Never stretch an existing rounded-corner "Subtract" bezel to a new size** — a non-uniform resize squashes the round corners into ellipses. Rebuild it at each new size instead: an outer rect at `(-8,-8, W+16, H+16)` minus an inner rect inset by the brand's fixed border (commonly 52-60px) with `cornerRadius: 80`, combined via `figma.subtract()`.
- **`figma.subtract()` returns its result positioned in page-absolute coordinates, not relative to whatever frame you intended as its parent.** Set `node.x`/`node.y` explicitly right after the call (e.g. back to `-8, -8`) or the bezel renders off-canvas. Related: build the input rectangles' `x`/`y` *after* `appendChild`-ing them into the target frame, not before — setting position pre-parent then calling `subtract()` can produce wrong relative coordinates in the result.
- **A shape's raw `x`/`y`/`rotation` can be actively misleading.** A repeating end-card glow ellipse looked, by its raw coordinates, like it sat almost entirely below the frame — it actually carries `scaleY: -1` (a vertical mirror), which puts its real bounding box back inside the frame once you read `relativeTransform` instead of the raw fields. Likewise, a "sublinhado" vector with `rotation: -180` was really a horizontal mirror (`a: -1` in the matrix) — it renders from `(x - width)` to `x`, the opposite of what the raw rotation number suggests. Always derive the real bounding box from the transform matrix before centering/aligning anything against a rotated or mirrored shape.

## Reading the source scenes correctly (before touching anything)

- **Off-canvas leftovers are common and must not be reproduced.** Sequential video-storyboard frames ("MOBITE" sections) routinely carry a full extra copy of text/graphics from the adjacent scene, deliberately parked off-frame (commonly `x ≈ -1677` or `x ≈ -2103`, sometimes `y` beyond the frame height) so the next scene's animation has something to slide in from. Always confirm with `get_screenshot` of the *original* 16:9 frame — never infer visibility from a bounding box alone.
- **Z-order hides things too, not just position.** More than once a text node or icon sat well inside the frame's 0–2560/0–1440 bounds but was fully covered by an opaque sibling drawn on top of it in z-order — invisible in the render despite "valid" coordinates. Cross-check an isolated screenshot of the suspect layer, not just its coordinates.
- **Word-swap / reveal animations leave both words in the file at once.** Tell the active word from the outgoing "ghost" by its `fills`: a `GRADIENT_LINEAR` fill that fades to transparent starting from the very beginning of the word marks the outgoing ghost layer; a solid fill, or a gradient that stays opaque until near the very end of the word, marks the active/legible layer. Confirm against the rendered screenshot, don't guess from z-order or node name.
- **"Carousel" cards often nest their real headline one level deeper** than the top-level 16:9 frame — inside a sub-frame like `Frame 1410128239/241/242`. A flat, direct-children-only scan misses this; recurse with something like `frame.findAll(n => n.type === 'TEXT')` before concluding a scene "has no text."
- **Decorative bleed elements are usually intentional, not cruft.** A thin sliver of a plant photo hanging off a frame's edge, or a huge blurred glow mostly outside the frame, generally reads as a deliberate accent once you look at the actual render — confirm with a screenshot before stripping something out as "obviously off-canvas garbage." Off-canvas ≠ unintentional; check what it contributes to the visible crop before judging it.

## Canvas sizes and margins used this session

- New sizes: **1440×2560** for 9:16, **1440×1440** for 1:1 — chosen to share the "1440" dimension with the source 2560×1440 16:9 masters, so there's no resampling factor to reason about between formats.
- Safe text margin, **9:16 only**: exclude y=0–267 (top) and y=2227–2560 (bottom). This scales the client's stated 250px-bottom / 200px-top brief (given at an assumed 1080-wide convention) up by the 1440/1080 ≈ 1.333 factor. 1:1 carries no mandated margin — ~80-120px of breathing room from the edges was used as an informal target.
- When a background photo/gradient needs to fill the new canvas without empty gutters, prefer a real cover-crop (recompute the fill's `imageTransform`/`scaleMode: 'FILL'` from the image's actual pixel dimensions) over a naive stretch — a couple of source `imageTransform`s already carried a small unintended distortion that's worth not perpetuating.

## Figma MCP / Dev Mode quota

Mid-session, several agents hit: `"You've reached the Figma MCP tool call limit for your Full seat on the Professional plan."` This is a plan/seat-tier cap on Dev Mode MCP Server tool calls, unrelated to how many people are using the account — a single heavy session with many parallel agents can exhaust it on its own. Two things worth knowing:

- It appears to be a **separate quota** from the general "usage credit" banner shown in the Figma app (which can show a non-exhausted percentage, e.g. 77% with a 12-day reset, even while the MCP-specific limit is fully blocking). Check the account's usage/billing breakdown for a line item specific to "Dev Mode MCP Server" rather than trusting the general banner alone.
- **The failing script is atomic — no partial writes happen.** It's safe to just re-run the exact same agent/call once the quota clears; nothing needs to be undone or re-verified first. In this session, a page refresh on the Figma account was enough to restore calls (whatever the underlying mechanism was), and every blocked agent resumed cleanly from its documented state.
